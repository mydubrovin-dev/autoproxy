# autoproxy

Скрипт для разворачивания на свежем CentOS/Rocky/RHEL VPS готового
прокси-сервера в один шаг. Скачали и запустили один скрипт — всё
остальное настраивается само, кроме одного интерактивного шага для
настройки MTProto/SNI (см. ниже).

## Что разворачивает

0. При необходимости **создаёт swap** (см. раздел ниже), **обновляет
   систему** (`dnf update -y`, кроме `openssh*` — см. раздел ниже),
   **отключает IPv6** и переводит fail2ban на бан через **firewalld**
   (вместо голого iptables/ip6tables).
1. **Squid** — forward-прокси с авторизацией по логину/паролю. В интернет
   пропускаются только авторизованные клиенты.
2. **[MTProto FIX by MEKO](https://github.com/Mekotofeuka/MTPROTO_FIX_By_MEKO)**
   в Docker-контейнере (`--network host --cap-add NET_ADMIN` — нужно,
   потому что фикс правит iptables на хосте).
3. **fail2ban** — следит за sshd и банит тех, кто ломится по SSH.

## Использование

Перед запуском — вручную, из консоли хостинга/гипервизора (не по SSH,
см. [почему](#обновление-системы-и-openssh) — ниже), обновите систему
и перезагрузитесь:

```bash
rpm -q network-scripts && systemctl is-active --quiet NetworkManager && dnf remove -y network-scripts
dnf update -y
reboot
```

Здесь известный конфликт на Rocky/RHEL 9: устаревший `network-scripts`
пинит старую версию `initscripts` и блокирует апдейт без её удаления.
`dnf` в сообщении об ошибке сам предлагает `--allowerasing` — **не
делайте так**: это разрешает dnf стереть вообще любой конфликтующий
пакет по своему выбору, а не именно `network-scripts`. На практике dnf
может вместо него снести `NetworkManager` (или его зависимость) —
именно так один раз уронило сеть на боевой машине. Правильно — убрать
`network-scripts` явно по имени, и только если сетью реально управляет
`NetworkManager` (проверка `systemctl is-active` выше как раз это
гарантирует).

Затем, на свежей машине CentOS/Rocky/RHEL, от root:

```bash
curl -fsSL https://raw.githubusercontent.com/mydubrovin-dev/autoproxy/main/install.sh | sudo bash
```

Необязательные переопределения (переменные окружения, задать перед пайпом):

| Переменная              | По умолчанию | Описание                     |
|--------------------------|--------------|--------------------------------|
| `AUTOPROXY_SQUID_USER`     | `proxyuser`  | Логин для Squid              |
| `AUTOPROXY_SQUID_PASS`     | случайный    | Пароль для Squid              |
| `AUTOPROXY_SQUID_PORT`     | `3128`       | Порт, на котором слушает Squid |
| `AUTOPROXY_TRUSTED_IPS`     | (пусто)      | Доп. IP/подсети, которые fail2ban никогда не забанит (через пробел), в дополнение к дефолтным |
| `AUTOPROXY_SKIP_UPDATE`     | (пусто)      | `1` — пропустить `dnf update -y` в начале установки |
| `AUTOPROXY_MTPROTO_PORT`     | `443`        | Порт MTProto, который `install.sh` открывает в firewalld (порт самого SYN FIX задаётся в меню MEKO и сохраняется в его скрипте) |

Учётные данные Squid всегда сохраняются в
`/root/autoproxy/squid-credentials.txt` (доступ только root, права 600),
независимо от того, были они сгенерированы автоматически или заданы вручную.

### Управление пользователями Squid

Логины/пароли для Squid живут в отдельном текстовом файле
`/etc/autoproxy/squid-users.txt` — не нужно лезть в `htpasswd` или
`/etc/squid/passwd` руками.

Формат — по одной паре `логин:пароль` на строку, пароль в открытом
виде (хешируется при применении), пустые строки и строки с `#`
игнорируются:

```
# /etc/autoproxy/squid-users.txt
proxyuser:Xk9mPq2wRt7vLj4n
alice:another-password
bob:yet-another-password
```

После правки файла — применить и перезапустить Squid одной командой
(ставится установщиком в `/usr/local/bin`):

```bash
autoproxy-squid-users
```

Скрипт **полностью пересобирает** `/etc/squid/passwd` из этого файла
и делает `systemctl reload squid` (если reload недоступен — `restart`).
Значит: убрали строку — пользователь теряет доступ; добавили — сразу
получает. При первой установке файл создаётся автоматически с той же
парой логин/пароль, что и в `squid-credentials.txt`.

### Swap на маленьких VPS

На тарифах с 512МБ–1ГБ RAM без swap `dnf update -y` регулярно падает
под OOM killer — сама только `dnf`-транзакция полного обновления
системы стабильно упирается в 600-700МБ RSS (воспроизведено на живой
машине с 929МБ RAM: `dmesg` показывал `Out of memory: Killed process
... (dnf)`). `docker build` позже может добавить похожую нагрузку.

`install.sh` теперь сам проверяет это первым делом: если swap нигде не
подключён (`swapon --show` пусто) и всего RAM меньше 2ГБ — создаёт
своп-файл на 2ГБ (`/swapfile`, добавляется в `/etc/fstab`, переживает
перезагрузки). Если у вас уже есть свой swap или RAM ≥ 2ГБ — шаг
пропускается, ничего не трогается.

### Обновление системы и openssh

Рекомендуется обновить систему и перезагрузиться **вручную, до**
запуска `install.sh` (см. [Использование](#использование)) — так
любое обновление ядра/OpenSSL/openssh применится штатно, с
перезагрузкой, а не посреди работы скрипта.

Сам `install.sh` делает то же самое (точечно убирает
`network-scripts`, если это безопасно, без `--allowerasing`), и тоже с
`--exclude='openssh*' --exclude='NetworkManager*'`. Исключение openssh
намеренное: при обновлении пакет
вызывает `systemctl try-restart sshd`, то есть **полный перезапуск
демона**, а не reload — если скрипт запущен через `curl | sudo bash`
по SSH (обычный случай), это оборвёт текущую сессию прямо посреди
установки, и скрипт не дойдёт до конца.

Если `openssh*` всё же успел устареть — обновляйте его отдельно и
осознанно, желательно не по SSH, а из консоли хостинга/гипервизора (в
Proxmox — Console/noVNC у самой VM):

```bash
dnf update -y 'openssh*'
systemctl restart sshd
```

### Белый список fail2ban

По умолчанию fail2ban никогда не банит:

```
127.0.0.1/8  ::1
81.211.68.176/28  212.24.52.192/28  217.22.164.0/28  77.51.177.18/32
```

Добавить свои адреса — через `AUTOPROXY_TRUSTED_IPS` (не заменяет
дефолтный список, а дополняет его):

```bash
AUTOPROXY_TRUSTED_IPS="203.0.113.5 198.51.100.0/24" \
  curl -fsSL https://raw.githubusercontent.com/mydubrovin-dev/autoproxy/main/install.sh | sudo bash
```

Правило `[sshd]` в MEKO/iptables-фиксе SSH-порт не трогает (в
`data/rules.sh` он явно добавляет `ACCEPT` для SSH перед лимитами) —
если после установки SSH недоступен, почти наверняка забанил именно
fail2ban. `install.sh` при каждом запуске снимает все текущие баны
(`fail2ban-client unban --all`), так что повторный запуск скрипта
разблокирует доступ.

### IPv6 и firewalld

На Rocky/RHEL с включённым IPv6 firewalld периодически падает с
ошибками про `ip6tables` (нет реального IPv6-трафика, а firewalld всё
равно пытается им управлять). `install.sh` поэтому:

- **Отключает IPv6** — сразу через sysctl
  (`/etc/sysctl.d/99-autoproxy-disable-ipv6.conf`) и на уровне ядра
  через `grubby --update-kernel=ALL --args="ipv6.disable=1"` (для
  полного эффекта после перезагрузки).
- Ставит `IPv6_rpfilter=no` в `/etc/firewalld/firewalld.conf`, чтобы
  firewalld не пытался обслуживать несуществующий IPv6-стек.
- Переключает fail2ban на бан через firewalld
  (`banaction = firewallcmd-ipset` вместо голого iptables), чтобы
  fail2ban и firewalld не боролись за одни и те же правила. Squid уже
  и так открывает порт только через `firewall-cmd`.

Всё это выполняется до установки Squid/fail2ban, поэтому даже при
первом запуске конфликтов быть не должно.

**Побочный эффект, если Docker уже был установлен:** перезапуск
firewalld после того, как Docker уже поднял свои NAT/masquerade-правила
для bridge-сети, эти правила стирает — а именно bridge-сетью (не
`--network host`) пользуется песочница `docker build`. Симптом —
`docker build` падает с `Temporary failure resolving 'deb.debian.org'`
и подобным, хотя обычные контейнеры с `--network host` продолжают
работать. Поэтому `install.sh` при каждом запуске делает
`systemctl restart docker` (а не только `enable --now`, который ничего
не сделает, если Docker уже запущен) — это пересоздаёт правила заново.
Если у вас всё ещё старая версия скрипта и `docker build` падает
именно так — просто `systemctl restart docker` вручную и повторите
установку.

**Порт MTProto (443 по умолчанию) тоже открывается в firewalld** —
раньше `install.sh` открывал только порт Squid, и порт MTProto нужно
было добавлять руками (`firewall-cmd --add-port=443/tcp --permanent`).
Если у вас всё ещё старая версия скрипта — либо откройте порт вручную,
либо просто перезапустите `install.sh`, он сам это сделает.

## Настройка MTProto / SNI (пошагово, вручную)

Установщик MEKO — интерактивное меню без флагов для автоматического
режима, поэтому `install.sh` только готовит контейнер, а саму настройку
нужно один раз пройти руками. Ниже — точный путь по меню (проверено по
исходникам MEKO Manager v1.95, ветка проверялась на движке Telemt; для
MTG/MTProto.zig пункты 4–6 будут отличаться, а всё остальное так же).

1. Зайти в контейнер и запустить установщик:

   ```bash
   docker exec -it autoproxy-mtproto bash /tmp/meko-install.sh
   ```

2. В меню **MEKO MANAGER V1.95** нажать **1** (или просто Enter) — «Меню proxy».
3. В меню proxy нажать **1** (или Enter) — «Стандартная установка
   (рекомендуется)». Скрипт скачает MEKO Manager и сам откроет его меню.
4. В главном меню MEKO Manager нажать **3** — «Меню прокси и настройки
   конфигов».
5. Выбрать движок — например **1** (Telemt Menu); либо **4** (MTG),
   **3** (MTProto.zig).
6. В меню движка (Telemt) нажать **1** — «Установить/обновить/откатить
   Telemt» — и пройти мастер установки. Когда он спросит домен
   (SNI / FakeTLS), указать:

   ```
   www.ite-ng.ru
   ```

7. Там же пункт **8** управляет mss/mss_bulk/synlimit и **зависит от
   текущего состояния конфига**:
   - Если написано **«Отключить mss, mss_bulk и synlimit»** — они
     сейчас включены, нажмите **8**, чтобы выключить (рекомендуется,
     иначе будет низкая скорость загрузки медиа).
   - Если написано **«Включить mss и mss_bulk (не рекомендуется)»** —
     они уже выключены по умолчанию, **ничего нажимать не нужно**;
     нажатие **8** в этом случае их, наоборот, включит.
8. Вернуться в главное меню (**0** — «Назад в прокси меню», затем **0** —
   «Назад») и нажать **1** — «Меню установки MTProto FIX», чтобы применить фикс.
   Дальше спросит вариант правил — берите **[4] v3 фикс nftables
   (рекомендуется, совместим с Docker)**. Детект iOS у него тот же
   алгоритм (по байтам, u32), что и у пункта [1], просто через
   nftables вместо iptables — единственный из «рекомендуемых»
   вариантов, который сам MEKO помечает как совместимый с Docker
   (у нас именно такой контейнер: `--network host --cap-add NET_ADMIN`),
   и он чище уживается с firewalld на хосте (тоже на nftables-бэкенде).
   [2] (zapret2) отмечен «на этапе тестирования» — не для прода;
   [3]/[5] — устаревший алгоритм детекта (TTL+Length), менее точный.

   На старых образах после выбора варианта меню могло вылетать с
   `line 551: systemctl: command not found` — причина и фикс описаны
   ниже; на актуальном образе такого быть не должно.
9. В главном меню нажать **7** — «Проверить домен для прокси» — и
   проверить `www.ite-ng.ru`: должно быть «🟢 Маркер: НЕТ» (если нет —
   в п.6 нужно будет указать другой домен).

Снова открыть меню в любой момент можно так:

```bash
docker exec -it autoproxy-mtproto mekopr
```

### Перенос существующих пользователей Telegram (с их ключами)

Пользователи Telemt живут в `/etc/telemt/telemt.toml`, секция
`[access.users]`, одна строка на пользователя — **имя и ровно 32
hex-символа секрета**:

```toml
[access.users]
hello = "0123456789abcdef0123456789abcdef"
alice = "fedcba9876543210fedcba9876543210"
```

Обычно же «ключ» пользователя у вас на руках в виде `имя : ключ`, где
ключ — это **полный секрет из ссылки подключения** (`secret=...` в
`tg://proxy?...` / `t.me/proxy?...`), а он состоит из **трёх склеенных
частей**:

```
ee  0123456789abcdef0123456789abcdef  7777772e6974652d6e672e7275
└┬┘ └──────────────┬───────────────┘  └────────────┬───────────┘
префикс        сам секрет             домен FakeTLS в hex (здесь www.ite-ng.ru)
(2 симв.)     (32 hex-символа)
```

В `telemt.toml` нужна **только средняя часть** — 32 символа секрета.
Первые два символа (`ee`; в режиме secure — `dd`) и хвост с доменом
нужно **вырезать**. Если у человека уже «голый» ключ из 32 символов —
берётся как есть (не отрезайте от него `ee`: у настоящего секрета эти
символы могут быть просто началом).

Вырезать руками из полного ключа: символы с 3-го по 34-й:

```bash
echo 'ee0123456789abcdef0123456789abcdef7777772e6974652d6e672e7275' | cut -c3-34
# 0123456789abcdef0123456789abcdef
```

А хвост (символы с 35-го) — это домен, его можно расшифровать и
проверить:

```bash
echo 'ee0123456789abcdef0123456789abcdef7777772e6974652d6e672e7275' | cut -c35- \
  | python3 -c 'import sys; print(bytes.fromhex(sys.stdin.read().strip()).decode())'
# www.ite-ng.ru
```

**Важно про домен.** Секрет в ссылке пользователя «запоминает» домен, с
которым клиент идёт на сервер (SNI). Если он **не совпадает** с
`tls_domain` в `telemt.toml`, Telemt отбрасывает такое подключение
(`TLS handshake rejected by unknown SNI policy ... Unknown TLS SNI` в
`/var/log/telemt.log`). Поэтому либо хвост старых ключей расшифровывается
в тот же домен, что стоит у вас в `tls_domain` (`www.ite-ng.ru`) — тогда
старые ссылки продолжат работать без правок на клиентах, — либо
пользователям придётся выдать новые ссылки (с новым доменом). Один
экземпляр Telemt работает с одним `tls_domain`.

**Массовое добавление.** Положите ключи в файл `tg-users.txt` (по
строке `имя : ключ`, пробелы вокруг `:` не мешают, ключи можно в
любом из видов выше) и сгенерируйте строки для конфига:

```bash
while IFS=: read -r name key; do
    name=$(echo "$name" | xargs); key=$(echo "$key" | xargs | tr 'A-F' 'a-f')
    [ -z "$name" ] && continue
    [ "${#key}" -ne 32 ] && { key=${key#ee}; key=${key#dd}; }   # полный ключ -> срезаем префикс
    secret=${key:0:32}                                          # и хвост с доменом
    [[ $secret =~ ^[0-9a-f]{32}$ ]] || { echo "# ПРОПУЩЕНО (не 32 hex): $name" >&2; continue; }
    [[ $name =~ ^[A-Za-z0-9_-]+$ ]] || name="\"$name\""         # нестандартные имена — в кавычки
    echo "$name = \"$secret\""
done < tg-users.txt > new-users.txt

cat new-users.txt        # глазами проверить результат
```

Затем вставить эти строки в секцию `[access.users]` и перезапустить
Telemt. (`/etc/telemt` смонтирована с хоста, так что файл можно править и
напрямую: `nano /etc/telemt/telemt.toml`; команды ниже — то же самое
через контейнер.)

```bash
docker cp new-users.txt autoproxy-mtproto:/tmp/new-users.txt
docker exec autoproxy-mtproto sed -i '/^\[access\.users\]/r /tmp/new-users.txt' /etc/telemt/telemt.toml
docker exec autoproxy-mtproto chown telemt:telemt /etc/telemt/telemt.toml
docker exec autoproxy-mtproto pkill telemt      # supervisor поднимет заново в течение ~10 с
sleep 12 && docker exec autoproxy-mtproto tail -5 /var/log/telemt.log
```

Имена в `[access.users]` должны быть **уникальны** (в том числе не
совпадать со стандартным пользователем `hello`, который создаёт
установщик Telemt — при совпадении TOML не распарсится и Telemt не
стартует; ненужного `hello` проще удалить:
`docker exec -it autoproxy-mtproto nano /etc/telemt/telemt.toml`).
Одного пользователя можно добавить и вручную через `nano` в той же
секции. Ссылку подключения для любого пользователя можно напечатать
из меню: `mekopr` → `[3]` → Telemt → `[7]`.

### Почему в контейнере нет systemd, и как это не ломает персистентность

MEKO и сам Telemt рассчитаны на systemd — им нужен, чтобы
пересоздавать сервис/правила автоматически после перезагрузки. Пихать
полноценный systemd внутрь Docker-контейнера (PID1 = systemd,
`--privileged`, cgroup-мониты) — рабочий, но откровенно тяжеловесный
вариант для этой задачи, поэтому мы туда не идём. Вместо этого три вещи:

- **`docker/mtproto/systemctl-shim.sh`** ставится в образ как
  `/usr/local/bin/systemctl` — фейковый `systemctl`, который тихо
  отвечает "успех" на любую команду. Без него не только персистентность
  сломана: `main.sh` (сам менеджер MEKO) запускается с `set -eo pipefail`,
  а вызов `systemctl daemon-reload` в `rules.sh` (после выбора варианта
  SYN FIX) ничем не защищён — с отсутствующим `systemctl` (exit 127) это
  **валит весь процесс `main.sh`, то есть всё меню целиком**, а не
  просто печатает предупреждение (правила при этом уже успевают
  примениться, но продолжить работу в меню без перезапуска нельзя).
  С шимом команда просто успешно завершается, и меню не падает.
- **`/opt`** (сам MEKO-менеджер, рабочая директория Telemt,
  MTProto.zig) — именованный Docker-volume `autoproxy-mtproto-opt`, а
  **`/etc/telemt`** (конфиг/секреты Telemt) — обычная папка хоста
  `/etc/telemt`, смонтированная в контейнер по тому же пути. Даже когда
  `install.sh` пересоздаёт контейнер (`docker rm -f` + заново, это
  происходит при каждом перезапуске `install.sh`), эти данные не
  теряются. Конфиг можно читать и править **прямо на хосте**
  (`nano /etc/telemt/telemt.toml`, файл принадлежит пользователю
  `telemt` из контейнера — после правки с хоста владельца менять не
  нужно, если вы редактируете на месте) и включать в бэкапы как
  обычную папку. Если раньше конфиг лежал в старом volume
  `autoproxy-mtproto-etc-telemt`, `install.sh` один раз сам перенесёт
  его в `/etc/telemt` (только если папка пуста; старый volume не
  удаляется — можно убрать через `docker volume rm` после проверки).
  `/opt` при желании смотрится так: `docker volume inspect
  autoproxy-mtproto-opt --format '{{ .Mountpoint }}'`.
- Сам бинарник Telemt (лежит в `/bin`) **не** персистится — на Debian
  13 `/bin` это symlink на `/usr/bin` (merged-usr), монтировать туда
  volume рискованно (может перекрыть вообще все системные бинарники
  образа). Это не страшно: если после пересоздания контейнера
  `mekopr` пишет, что Telemt не установлен — просто зайдите в меню
  Telemt и нажмите **1** → Enter (последняя версия), это пара секунд.
- SYN FIX (то, что не смог сохранить как systemd-сервис
  `mtpr-nft-synfix.service` / `mtpr-synfix.service`) вместо этого
  **переприменяется самим `entrypoint.sh` при каждом старте
  контейнера**: юнит MEKO по сути лишь запускает сохранённый скрипт
  (`/opt/mtpr-simple/mtpr-synfix-nft.sh` для nftables или
  `/opt/mtpr-simple/apply-mtpr-synfix.sh` для iptables — лежат на
  volume `/opt`), его и запускает `entrypoint.sh`. Так сохраняется тот
  вариант, что вы выбрали в меню (раньше вызывался `main.sh
  -auto_install`, который всегда ставил iptables-вариант — из-за чего
  выбранный nftables после рестарта не поднимался). На простом
  `docker restart` это безобидный no-op (скрипты сами пересоздают свою
  таблицу/цепочку), а после **перезагрузки хоста** (netfilter
  стирается ядром) — восстанавливает защиту без захода в меню. Пакет
  `nftables` запечён в образ, чтобы скрипт работал и после
  пересоздания контейнера.
  Проверить статус: `docker exec -it autoproxy-mtproto mekopr` (шим
  `systemctl` отвечает «активен» по факту наличия таблицы/цепочки, так
  что в шапке меню будет «Установлен», а не «сервис не запущен»), либо
  `nft list table inet mtpr_synfix` на хосте.
- **Сам процесс Telemt тоже никто не запускает без systemd/openrc** —
  это отдельная проблема от SYN FIX. У апстримного установщика Telemt
  (`install_service()`) при отсутствии обоих просто печатает подсказку
  «запустите вручную» и на этом останавливается — бинарник не
  стартует вообще. Поэтому `entrypoint.sh` держит свой цикл-supervisor:
  каждые 10 секунд проверяет, жив ли `/bin/telemt`, и если нет —
  перезапускает его от пользователя `telemt` (создаётся установщиком
  Telemt). Работает независимо от того, что показывает пункт
  «Перезапустить Telemt» в меню (он дёргает уже зашимленный `systemctl`,
  который ничего реально не делает) — реальный перезапуск всегда за
  этим циклом. **MTG и MTProto.zig таким же образом пока не
  супервайзятся** — если переключитесь на них, процесс тоже нужно
  будет держать живым каким-то другим способом.

## Структура проекта

```
install.sh              точка входа (именно этот файл вы скачиваете curl'ом)
lib/
  common.sh              логирование, проверка root/ОС, общие функции
  security.sh              firewalld, отключение IPv6
  squid.sh                установка и настройка Squid с авторизацией
  fail2ban.sh              установка fail2ban и jail для sshd (бан через firewalld)
  docker.sh                 установка Docker Engine
  mtproto.sh                 сборка и запуск контейнера MTProto-fix
docker/mtproto/
  Dockerfile                 образ для контейнера MTProto-fix
  entrypoint.sh                скачивает установщик MEKO, печатает инструкцию
  systemctl-shim.sh             фейковый systemctl (в контейнере нет systemd)
scripts/
  squid-users.sh              пересобирает /etc/squid/passwd из squid-users.txt,
                               ставится установщиком как autoproxy-squid-users
```

## Примечания

- Рассчитан на CentOS/Rocky/RHEL (`dnf`/`yum`). На Debian/Ubuntu не тестировался.
- Перед тем как пускать `install.sh` через `curl | bash` на важной машине,
  просмотрите его содержимое — обычная рекомендация для любого
  `curl | bash`-установщика, этот не исключение.
- Повторный запуск `install.sh` безопасен для Squid/fail2ban/Docker;
  контейнер MTProto каждый раз пересоздаётся с нуля (вся настройка MEKO
  внутри контейнера теряется — донастройте через `mekopr` заново).
